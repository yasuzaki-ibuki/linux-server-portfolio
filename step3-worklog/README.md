# Step 3:作業記録・障害報告アプリ

障害対応や作業の記録(事象・影響・原因・対処・再発防止)を、ブラウザで登録・閲覧できるWebアプリ。
これまでのサーバー構築で経験した障害5件を、初期データとして登録している。

## 構成

ブラウザ → Nginx(/worklog/)→ gunicorn(127.0.0.1:8002)→ Flask(app.py)→ SQLite(data/worklog.db)

## 機能

- 一覧表示(発生日時の新しい順、種別・ステータスで絞り込み)
- 詳細表示
- 新規登録・編集

## ファイル

| ファイル | 役割 |
|---|---|
| app.py | 画面の表示と、登録・編集の処理 |
| db.py | テーブルの定義と、データベースへの接続 |
| seed.py | 初期データ(これまでの障害5件)の登録 |
| templates/ | 画面(共通部分・一覧・詳細・入力) |
| worklog.service | systemdのサービス設定 |

## 設計・運用で工夫した点

- テーブル設計で NOT NULL・CHECK 制約を使い、不正なデータが入らないようにした
- SQLは値を直接埋め込まず、プレースホルダで渡す(SQLインジェクション対策)
- 画面表示はテンプレートの自動エスケープを利用(XSS対策)
- 入力チェックはブラウザ側だけでなく、サーバー側でも実施
- 登録・更新後は詳細画面へリダイレクトし、二重送信を防止(PRGパターン)
- SCRIPT_NAME を設定し、/worklog/ 配下での公開でもリンクが正しく作られるようにした
- systemdでサービス化(一般ユーザーで実行、自動起動、異常終了時の自動再起動)
- SELinuxの制約に合わせ、/home ではなく /opt に配置
- 監視(Step 2)の対象に追加し、停止試験で異常検知と復旧通知を確認
- データベースはGitHubに含めず、seed.py で初期状態を再現できるようにした

## 構築中に発生したトラブル

- 事象:新規登録画面を開くと Internal Server Error
- 調査:gunicornのログ(Traceback)の最終行で TemplateNotFound: form.html を確認
- 原因:テンプレートファイルの配置ミス
- 対処:templates/ に正しく配置して解決
- 学び:利用者に見える画面ではなく、アプリ側のログから原因を特定する
